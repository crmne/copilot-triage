Triage now knows what you have released. It reads your docs and code from the default branch, so it used to tell people a feature was already there when it was only on `main`. It also answers discussions it moves to issues, and keeps judging pull requests when CodeRabbit stops reviewing.

## New

- **Unreleased work is called unreleased.** Every assessment knows how far the default branch is ahead of your latest stable release, and a new `search_changes` tool says which release shipped a change or that it is still unreleased. A reply that cites your docs or code has to check first, so a request for something only on `main` now gets "this is on the default branch and not in v1.2.1 yet" instead of "already supported" or "this request is stale". By @crmne.
- **Pull requests get judged when CodeRabbit runs out.** CodeRabbit posts "Review limit reached" or "Reviews paused" as a comment and leaves no review. That notice now runs triage: the agent judges the change without CodeRabbit instead of waiting on it, and the card's next step says when to ask CodeRabbit again with `@coderabbitai review`. Nothing is blocked from merging. If your workflow calls `assess.yml@v0`, this works after the update; if you call the action directly, let `issue_comment` events from `coderabbitai[bot]` through. By @crmne.

## Fixed

- **Moved discussions get an answer.** An issue created with the workflow token starts no workflow, and triage skipped issues a bot opened, so a discussion moved to an issue was never answered there. The run that moves a discussion now triages the new issue as if its author had just opened it, and later comments on it are triaged too. By @crmne.

Verified with RuboCop and 371 specs, the offline reply evaluation, and live runs of the new unreleased-feature case, where every run checked `search_changes` and told the reporter the feature was not in their release. Moving a real discussion was not tried end to end, since it creates a real issue.
