A push to a pull request no longer starts a job where Copilot does not review, recaps now say they are recaps, and triage catches more things we caught by hand: a required checkbox left unticked, a stacked pull request still carrying commits that were already squash-merged, an umbrella issue left open after all its work shipped, and a request already built on the default branch.

## New

- **A push starts a job only where Copilot reviews.** A push to a pull request only asks Copilot to review the new commit, yet it started a job in every repository; on RubyLLM, where Copilot never reviews, those jobs queued for over an hour behind tests. Set `reviews` (`copilot`, `private`, or `off`) in your triage and sweep workflows instead of in `.github/triage.yml`, and GitHub skips a push's job before it starts wherever Copilot does not review. Where it does, the fresh review is still requested within minutes, and the daily sweep re-requests one Copilot missed. A policy's `pull_requests.reviews` keeps working when the workflow leaves `reviews` out. By @crmne.
- **CodeRabbit's comments start no job.** Only CodeRabbit's notice that it will not review a commit starts a triage job now; its other comments used to start one each, spending billed minutes in private repositories. By @crmne.
- **Recaps say so.** The recap of a long new issue now starts with "Recap:", so reporters and maintainers can tell it apart from a question or an answer at a glance. A recap may also say what the reporter asks the maintainer to choose; one like that on ZapFast [#631](https://github.com/crmne/zapfast/issues/631) used to be dropped. By @crmne.
- **Requests already built.** When a short, clear request is already on the default branch but not in a release, triage tells the reporter instead of only labeling it. Spotifast [#1069](https://github.com/crmne/spotifast/issues/1069) got labels alone. By @crmne.
- **Required template checkboxes.** When a pull request leaves a required checkbox in your template unticked, such as "I understand and take responsibility for every submitted line", triage asks the author to tick it or say why it does not apply. It also asks about template sections left with their own prompt instead of an answer. Optional items and boxes that only describe the kind of change are left alone. ZapFast [#625](https://github.com/crmne/zapfast/pull/625) and [#637](https://github.com/crmne/zapfast/pull/637) went unasked. By @crmne.
- **Stacks after a squash merge.** When the pull request under a stack is squash-merged, the one above still holds its original commits, so updating the branch conflicts or duplicates code. Triage now names the merged pull request and asks the author to rebase with `git rebase --onto` past its last commit. TonePush [#37](https://github.com/crmne/tonepush/pull/37) and [#39](https://github.com/crmne/tonepush/pull/39) hit this. By @crmne.
- **Finished umbrella issues.** When the release pass checks an issue that tracks several pieces of work, and every pull request it lists is merged and released, triage asks once whether anything is left, so the reporter's answer can close it. TonePush [#28](https://github.com/crmne/tonepush/issues/28) stayed open after everything it tracked shipped. By @crmne.

Verified with RuboCop, 493 specs, the 36-case offline reply evaluation, and the live reply evaluation on `openai/gpt-5.6-luna` through OpenRouter. The live run passed 30 of 36; each of the six cases it missed, and the two new ones, then passed three reruns out of three. The new pull request facts were tested against recorded GitHub responses.

## Known limitations

- A stacked pull request hears about its squash-merged base the next time it is assessed, after a comment or a review, not the moment the base merges.
